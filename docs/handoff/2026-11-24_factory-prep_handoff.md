## 背景

- 富士カプセル北山工場の乾燥室で、タンブラー乾燥を16台の Raspberry Pi 4 カメラアレイ（e00〜e15）で無人撮影する。
  - 11/25(水)〜11/30(月)：赤カプセル、5ロット。11/25 に髙谷が設置する。
  - 12/11(金)〜12/16(水)：しずく型カプセル、5ロット。髙谷は出張しない。
  - 1ロット＝乾燥1回、20〜22時間。
- 計測中はネットワークを使えない。ポケットルータは設置時のみ使う。
- データは各 Pi の 1 TB SSD に記録し、12/16 以降に機材ごと返送してもらう。
- カメラは CAM-IMX296RAW（外部トリガで露光）。
- **トリガ箱は Arduino UNO R4 Minima**（AVR の Uno ではない）。FQBN は `arduino:renesas_uno:minima`。
- ユーザーの手元は **Windows PowerShell 5.1**。.ps1 は 5.1 と 7 の両方で動くように書く。
- Pi への ssh/plink は、ユーザーの PC からのみ届く。Claude のチャット環境からは届かない。

## 確定している仕様（実施計画書と一致させる）

| 項目 | 値 |
|---|---|
| 撮影 | 120秒ごとに2秒間の連続撮影（30 fps × 60枚） |
| 露光 | **30 ms**（トリガのパルス幅＝露光、16台共通）。現地で調整する。10 ms の整数倍に限る（50 Hz のちらつき対策） |
| 記録 | RAW10。各 Pi の SSD に、連続撮影ごとに npz を1ファイル |
| ロットの区切り | **撮影が5分以上止まったら、新しいセッションのフォルダに切り替える**（未実装。T1） |
| 容量 | 空きが 5 GB を切ったら撮影を止める（実装済み） |
| 時刻 | **RTC（DS3231）は取り付けない**（11/24 決定）。時計は fake-hwclock から再開する。実時刻との対応は、記録用紙のトグル ON 時刻と、バーストの回数×120 s で取る |
| READY 線 | **各 Pi の GPIO21（ピン40）、GND はピン34**（偶数列のみ。11/24 変更）。全台を1本に束ねて Uno の A0 へ。10 kΩ で Uno の **3.3 V** へプルアップする（5 V は不可） |
| READY 線の動作 | 撮影中以外は、各 Pi が GPIO21 を LOW に駆動する（`op dl`）。Ready のときは入力にして手放す（`ip pn`）。全台が手放したときだけ H になる |
| トリガ箱 | D13 同期出力、D2 トグル、D5/D6 2色LED、A0 READY。トグルとLEDは筐体の外に出す |
| トリガ箱のランプ | 緑点滅＝準備中／緑点灯＝待機／赤点灯＝撮影中／赤の速い点滅＝連続撮影中／赤緑交互＝起動5分後も全台そろわない。交互点滅は固定されない：全台そろえば自動で解除される |
| Pi 本体の LED | 緑点滅＝準備中／緑点灯＝撮影可能・撮影中／赤点滅＝SSD 未認識／赤点灯＝容量不足・異常 |
| Wi-Fi の優先度 | PiCamNet(100) > PiCamNet5G(99) > CIGL2.4 > CIGL5.0。CIGL は、Pi にプロファイルがある場合だけ順位を付け直す |

## 残タスク

### T1. ロットの区切りを10分から5分に【必須・11/25 より前】

- `capture/camera_agent.py`：`SESSION_GAP_S = 600.0` → `300.0`。直前のコメント（「10 min without a frame means a new run」）も直す。
- `readme.md`：95行付近の「10 min」を直す。
- `TRIGGER_TIMEOUT`（600 s、トリガが来ないときの警告）はそのままでよいか、ユーザーに確認する。
- 完了条件：トリガを6分止めると、次のバーストが新しいセッションフォルダに入る。4分止めたときは、同じフォルダに入る。

### T2. 30 ms 露光でフレームが抜けないかの確認【必須】

- 30 fps（周期 33.3 ms）で 30 ms 露光すると、次のトリガまでの余裕は約 3.3 ms しかない。
- 試し撮影で、1回の連続撮影につき全16台とも60枚そろうかを数える。数える小さなスクリプトがなければ作る（npz の `frames_raw` の枚数）。
- そろわない場合はユーザーに報告する。代案は「露光 20 ms」または「25 fps × 2.4 s」。勝手に仕様を変えない。

### T3. Pi・Arduino への反映（ユーザーが PC で実行する。Claude Code は手順の案内と結果の確認をする）

Pi を研究室の Wi-Fi につないだ状態で、`scripts/` から次の順に実行する。

```powershell
.\deploy_pull.ps1 -Branch thunder        # 全台が 426e457 以降で一致すること
.\deploy_ready_line.ps1 -Reboot          # gpio=21=op,dl を入れ、サービスを入れ直して再起動
.\deploy_ready_line.ps1 -Verify          # 全台 config=ok / unit=ok
.\deploy_picamnet.ps1 -Verify            # Wi-Fi の優先度を確認
.\deploy_arduino.ps1                     # e00 経由で R4 Minima に書き込む（初回は e00 にインターネットが要る）
```

- `deploy_arduino.ps1` は、最後に `EXP 30000 PERIOD 120000` が表示されれば成功。
- READY 線の配線が済むまでは、ランプは緑の点滅のままで正常。5分たつと交互点滅になるが、異常ではない。

### T4. 時刻に依存しない記録の補強【推奨・できれば 11/25 より前】

RTC を付けないため、Pi の時計は停電で最大約1時間戻ることがある。12/11 の再開時は 11/30 ごろの日付から始まる。

- npz に、`time.monotonic()` によるフレームごとの時刻と、`/proc/sys/kernel/random/boot_id` を追加する。既存の `timestamps` はそのまま残す。
- `make_session_dir()`：同じ名前のフォルダがすでにあれば、末尾に `_2` などを付けて別のフォルダにする（今は `exist_ok=True` で合流してしまう）。
- 解析側で新しいキーを読むかは任意。古い npz も読めるようにしておく。

### T5. 950 nm ロングパスへの差し替え（解析側）【12月の計測まで。11/25 には不要】

- 分光フィルタは **日東樹脂工業 CRALEX のロングパス（ハイパス）**。バンドパスではない。
  - ラベルの 750/800/850/900 は、NIR-75N/80N/85N/90N の呼び名（それぞれ 730/760/810/860 nm 以上を透過）。帯域は、隣のカメラとの差で取り出す。
- 750 のカメラ（e01, e03, e09, e11）を、Edmund の 950 nm ダイクロイックロングパスと NIR-90N を重ねたものに替える予定。取付時期はユーザーに確認する。
- `analyze/multispec_sa.py` と `analyze/sa_packed.py`：
  - `BAND_TILE` の 750 を 950 にする。ただし、11月のデータ（750 構成）も解析できるよう、計測ごとに構成を切り替えられるようにする。
  - 偽カラーも合わせて直す。
  - docstring の「band」という表現を、ロングパスの境目であることがわかる書き方にする。
- 差分で帯域を取り出す処理を加えるかは、ユーザーに確認する。
